# The robot

17 real CubeMars AK-series actuators, and every mass, inertia, envelope and
torque limit traced to either a datasheet or the CAD solids. Nothing here is a
plausible-looking number.

Everything in this directory except `climbing_env.py` is GENERATED from
[`../cad/`](../cad/README.md). Do not hand-edit.

    python cad/tools/gen_urdf.py     # links, meshes, joints, _actuators.json
    python urdf/_gen_scene.py        # scene.xml: walls, rungs, actuators, sensors
    python urdf/_gen_keyframe.py --write     # settle and verify the hang
    python cad/tools/verify.py       # 17 checks, source by source
    python -m rl.lessons             # the curriculum scenes

The robot this replaced - aluminium cylinders with masses and `effort=` values
derived from geometry, 11.13 kg, fine in simulation and impossible to build -
is in git history at the commit before this one.

| file | what it is |
|---|---|
| `climbing_robot.urdf` | fixed base |
| `climbing_robot_floating.urdf` | free base - **use this one for MuJoCo** |
| `scene.xml` | the corridor, the robot, 17 actuators, 86 sensors, a verified hanging keyframe |
| `lessons/` | the PPO curriculum, generated by `rl/lessons.py` (gitignored) |
| `meshes/<link>.stl` | visual: the bracket **and the vendor actuator geometry** |
| `meshes/<link>_col_<part>.stl` | one bracket part each; MuJoCo takes each one's convex hull for collision |
| `_actuators.json` | the actuator table: which motor, what it can do |
| `t_box.json`, `t_env.json` | the measured torque requirement the sizing is checked against |

mujoco.mj_resetDataKeyframe(m, d, 0)   # "hang_on_rung"

`climbing_env.py` and the RL task load against it unchanged.
Loading is not working, though: the first version of this model loaded cleanly

| | before | now |

| of which actuators | - | 12.73 kg (53 %) |
| of which structure | - | 7.88 kg (6061-T6; 1.59 of it the lidar mounts and cage) |
| of which payload | - | 2.50 kg (battery, compute, wiring) |
| of which lidars | - | 1.06 kg (4 × Livox Mid-360) |
| arm root to arm root | 0.310 m | 0.310 m |
| base to shoulder axis | 0.405 m | 0.405 m |
| hook reach below the finger axis | 0.150 m | 0.110 m |
| **vertical reach, one hand anchored** | **0.671 m** | **0.56 m** |
| centre of mass | - | x 0.6, y 0.0, z 165.9 mm (136.3 before the lidars) |

The reach is lower than both earlier figures, and both earlier figures were
wrong in the same direction. v1's 0.671 m came from a pose with the upper arm
through the torso. The first v2, abduction-first, measured 0.68 m because
raising its arm by abduction flipped a 104 mm shoulder link over the top and
lifted the arm's root 208 mm - a shrug no shoulder has, and the fold the user
saw in the video. Pitch-first keeps the root where a human's is, and four
seeds of `_reach.py` at 100k samples each agree on 0.555-0.562 m. Every rung
row in `scene.xml` and in the lessons below lesson 9 is 0.45 m apart; lesson
9's 0.75 m row was beyond static reach by design.

## The actuators

Three part numbers, one vendor, one CAN protocol, one driver family. All three
are high-ratio planetary units, not quasi-direct-drive — a climbing robot spends
its life holding a static load, which is what gear ratio buys and what QDD
gives away.

| | AK80-64 KV80 | AK60-39 V3.0 KV80 | AK45-36 KV80 |
|---|---|---|---|
| peak / rated torque | 120 / 48 N·m | 72 / 24 N·m | 24 / 8 N·m |
| no-load / rated speed | 7.85 / 5.03 rad/s | 10.3 / 7.33 rad/s | 5.45 / 4.19 rad/s |
| gear ratio | 64:1 | 39:1 | 36:1 |
| mass | 850 g | 750 g | 340 g |
| envelope | Ø98 × 61.9 mm | Ø79 × 67 mm | Ø55 × 54 mm |
| encoder | 14-bit | dual 21-bit | 14-bit |
| backlash | 0.18° | 15 arcmin | 12 arcmin |
| supply | 24/48 V | 48 V | 24 V |
| used at | 8 joints | 8 joints | 2 joints |

Sources: [AK80-64](https://www.cubemars.com/product/ak80-64-kv80-robotic-actuator.html),
[AK60-39](https://www.cubemars.com/product/ak60-39-v3-0-kv80-robotic-actuator.html),
[AK45-36](https://www.cubemars.com/product/AK45-36.html),
[AK series driver manual](https://store.tmotor.com/images/file/202205/311653967459529218.pdf).
Geometry: the vendor's own STEP files from [step.parts](https://www.step.parts),
sha256-verified, and their envelopes measured back off the files agree with the
datasheets to 0.1 mm (`cad/tools/verify.py`).

**Control interface** is the same for all three: CAN at 1 Mbps, with both a
servo mode (dual-loop, more accurate position and torque) and MIT mode
(single-loop position/velocity/torque with Kp/Kd, the interface a learned
policy wants). One bus, one driver library, 17 node IDs. The host command rate
is not quoted by the vendor and needs measuring on the bench — `scene.xml`
steps at 500 Hz, and if the bus cannot hold that the policy's action rate is
what has to change, not the physics timestep.

**Speed is not the binding constraint.** v1 assumed `velocity=3.0` rad/s
everywhere; the slowest of these three does 5.45 rad/s no-load. The 48 V rail is
what makes that true — AK60-39 at 24 V would be too slow.

**The mixed 24 V / 48 V rail is a real cost.** The two AK45-36 need a buck
converter off the 48 V pack. It buys 820 g at the far end of the arm, which is
worth more than the converter costs.

## Sizing: measured, not assumed

v1's `effort=` values came from "the whole robot hangs off this joint's distal
chain at maximum reach". That is the right model for a **free** arm and the
wrong one for a hanging robot, and it got the answer backwards: it put 68 N·m at
the shoulder and 13 N·m at the finger, when the shoulder is close to the load
line and the wrist is the joint the whole body dangles from.

`cad/tools/torque.py` measures instead. A body hanging off one hook is a
pendulum, so it rotates about the anchor until its COM is straight below. For
each joint, cut the robot there; whichever side does not contain the anchor is
the load; the hold torque is the moment of that load about the joint axis. Two
requirement sets come out of it:

- **full joint box** — the pose swept anywhere the limits allow
- **climbing envelope** — the hook only latches with the arm raised (v1's own
  finding), so shoulder flexion −170…−70°, elbow −90…0°, abduction ±45°

| joint | actuator | peak | rated | need (box) | need (env) | margin box | margin env |
|---|---|---:|---:|---:|---:|---:|---:|
| waist_yaw | AK60-39 | 72 | 24 | 0.0 | 0.0 | — | — |
| shoulder_abduction | AK80-64 | 120 | 48 | 60.0 | 54.3 | 2.00× | 2.21× |
| shoulder_flexion | AK80-64 | 120 | 48 | 34.7 | 28.6 | 3.46× | 4.19× |
| shoulder_rotation | AK80-64 | 120 | 48 | 57.1 | 48.7 | 2.10× | 2.46× |
| elbow | AK80-64 | 120 | 48 | 87.9 | 77.0 | **1.37×** | 1.56× |
| forearm_roll | AK60-39 | 72 | 24 | 29.0 | 26.8 | 2.48× | 2.68× |
| wrist_flexion | AK60-39 | 72 | 24 | 49.3 | 47.4 | 1.46× | 1.52× |
| wrist_deviation | AK60-39 | 72 | 24 | 32.6 | 31.1 | 2.21× | 2.31× |
| finger | AK45-36 | 24 | 8 | 16.3 | 16.3 | 1.47× | 1.47× |

The 4 lidars and their cage (2.65 kg, all of it on the upper torso) took every
hanging joint 11-12 % higher: the elbow's box margin from 1.53× to 1.37×, still
over the 1.3× `verify.py` asks for.

Pitch-first halved the shoulder flexion's worst case (74.4 -> 34.7 N·m): its
axis now runs through the arm's root instead of 104 mm below the abduction one.

Margins are against PEAK torque, which is the right test for a hold that lasts
seconds. Against the CONTINUOUS rating the elbow, shoulder rotation and both
wrist joints are over - the elbow wants 77.0 N·m where the AK80-64 is rated 48.
A hang that has to last minutes needs either a brake or the next size up; that
is a decision, not an oversight, and it is the same one v1's numbers implied.

Three things this table says that are worth keeping:

1. **waist_yaw carries no gravity moment at all.** Its axis is vertical and
   gravity is vertical. It is sized for turning the body's inertia against the
   torso-on-wall friction, not for holding anything, and 72 N·m is generous.
2. **The elbow is the most loaded joint, not the shoulder** — lever 0.370 m at
   the hang equilibrium versus 0.267 m at the shoulder. The elbow sticks out
   sideways from the load line; the shoulder sits near it.
3. **Continuous holding is not the binding case.** Resting on two hands halves
   the load, and a well-postured rest drives it near zero, so the rated column
   only has to cover the two-hand hang: worst is wrist_flexion at 24.7 N·m (half
   its one-hand need) against 24 N·m rated - at the rating now, where it had 3 N·m
   to spare before the lidars; the settled keyframe hang asks 4.3 N·m of any joint.
   The single-hand reach is seconds at a time and is sized against peak.

**What a thin margin actually costs.** If the elbow cannot hold a pose, the arm
sags toward a lower-torque configuration — the robot does not fall, it just
loses that pose. The joints that would drop the robot are the ones holding the
hook on the rung (finger 1.66×, wrist_flexion 1.70×, wrist_deviation 2.59×), and
those have the margin.

## The lidars

Four Livox Mid-360 (265 g, 65 × 65 × 60 mm, Livox's own STEP) on the upper torso,
for the SLAM and the wall map (`cad/src/lib/lidar.py`, `cad/src/lib/spec.py`
`LIDARS`): two on a roof over the head, 45° toward the wall and 45° away, and one
sunk into the chest and one into the back, only their windows outside. A cage of
Ø16 × 2 mm 6061 tube guards all four: a bent bar up each corner of the torso,
40 mm proud of the panels, and a ring at z 0.345 m over the head joining their
tops (the height the ray-casting study picked: lower costs the head lidars 8 % of
what is above the hands).

What the simulation has of them:

| | scene.xml (C) | the MJX robot (`rl/mjx_scene.py`) |
|---|---|---|
| mass, inertia | each a uniform 265 g block, on `torso_upper`; mounts and cage from the solids | the same |
| cage | 16 capsules on the tubes' centre lines (`guard_*`), exact but at the bends: the foot bend's corner stands 8 mm proud along its diagonal | the same 16, paired with every rung slot and wall: 1143 → 1271 pairs |
| lidars | a box (the body) and a cylinder (the window) each, `lidar_*_body` / `_window` | none: inside the cage |
| the head's roof | one hull | none |
| the hats in the chest | none: inside the torso | none |
| where they look | a site each at its optical origin, z its axis (`lidar_head_front`, ...) | the same |
| what blocks them | an `occ_*` site per collision geom (group 5, 103 of them): motors as their cylinders, hooks their boxes, tubes their capsules, bracket parts their tightest box | the same sites |

The visual mesh draws each lidar as its envelope (body, window, M12 plug): Livox's
STEP is 54 000 triangles a unit and four took `torso_upper.stl` past MuJoCo's
200 000. The exact part is in `cad/STEP/robot.step`. `rl/lidar.py` casts the rays;
`rl/README.md` says what the policy gets from them.

## What moved, and why

Every offset below differs from v1 because two real actuator bodies could not
occupy the same space. Two actuators on perpendicular axes clear each other only
if their axis lines are at least r₁ + r₂ + 3 mm apart, or their finite bodies
miss along the link. `cad/tools/check_fit.py` checks this on solids — the
analytic version got it wrong for perpendicular axes, which is why it is a
boolean intersection now.

| offset | v1 | v2 | forced by |
|---|---|---|---|
| first shoulder joint | abduction, y ±0.155 z 0.165 | **flexion, y ±0.085 z 0.165** | pitch-first, like 10 of 12 humanoids surveyed: the pitch actuator's body inboard in the chest |
| `shoulder → shoulder_abduction` | 0 | **y ±0.070**, z 0 | the roll actuator beside the pitch output: its 49 mm radius + 1.5 + a 16 mm web + 2 + 1.5 |
| `wrist → wrist_deviation` z | −0.020 | **−0.084** | two Ø79 actuators need 82 mm |
| `wrist_dev → finger` z | −0.020 | **−0.072** | Ø79 + Ø55 need 70 mm |
| torso_upper | 0.240 wide | **a box 0.140 × 0.166 × 0.219** | its side walls are the pitch actuators' mounting plates |
| lower torso width | 0.210 | **0.180**, corners rounded to R90 | the waist turns the arms over a *stationary* lower torso; the elbow actuator sweeps a circle of radius 93.1 mm, so nothing may stick out past 90 mm |

The first two cancel: the arm's root is at y = ±0.155, world z = 0.405,
exactly where v1 put it. **Everything between the shoulder and the wrist is
dimensionally identical to v1.** The first v2 got there the other way round -
abduction first on a torso 104 mm taller, flexion 104 mm below it - and raising
that arm folded it up past its own abduction motor; the shoulder was rebuilt
pitch-first after the user saw it in a video (`cad/src/lib/spec.py`). Only the wrist stack is longer, by 116 mm, because three actuators
in series need more than 40 mm.

Two joint limits also moved, both measured:

- **shoulder_flexion −180 → −170°.** v1's README said not to go there: at −180
  the torso hangs flat against the wall and rams the rung below. (Pitch-first,
  the true CAD is clear to −180; abduction-first, the rotation actuator also
  grazed the abduction one past −173.)
- **shoulder_abduction inward −12° (right: +12°).** The upper arm's cheek meets
  the shoulder bracket's web from −15 (`check_pair.py`); the humanoids surveyed
  stop inward at −7 to −25. With the arm hanging straight down the body stops it
  sooner - the forearm meets the lower torso from −5 - as a human's arm meets
  its side.
- **elbow −120 → −110°.** −118 is where the two actuator bodies touch; −112.3 is
  where the two brackets do (the forearm web sweeps into the Ø72 plate on the
  shoulder-rotation flange). −110 leaves ~2.8 mm; the climbing envelope only uses
  −90…0.


### The hook is bolted on turned over

`spec.MOUNT_ROT` turns each hook's frame 180° about the forearm axis relative to
its finger joint — `quat="0 0 0 1"` on the hook body, `rpy="0 0 π"` on the finger
joint in the URDF, and the hook's plate still on the flange side of its actuator
(`build.in_turned_frame`: the plate overlaps the actuator by exactly what the
unturned hook did, where turning the frame alone would have put 21 700 mm³ of it
inside the motor). v1 found why (`rl/README.md`, the elbow section): raised
overhead, an unturned hook's throat faces away from the wall, and turning it back
through the arm pins the shoulder rotation at its stop and aims the elbow at the
wall. The first version of this model had dropped it — it lived only in v1's
hand-edited `scene.xml` — and the hang keyframe it settled into had the throat
facing the robot, the shank between rung and wall and both wrists on the wall.

### Collision: one convex hull per CAD part

MuJoCo collides the convex hull of a mesh, never the mesh. Exported as one mesh per
link, the first v2's torso frame was one hull — a block out to the shoulder
plates — and the raised upper arm's hull sank 10–22 mm into it at every flexion
past −120°, 18–52 mm from any real metal. The hang keyframe pressed the arms into
the torso with 1500 N and held four shoulder actuators at 88 % of peak torque
doing it. Every bracket part is its own mesh now
(`meshes/<link>_col_<part>.stl`, stored as its hull): the chest is six plates, and
a plate's hull is the plate. Over 1500 random poses of the climbing envelope, the
contacts MuJoCo reports that the true meshes do not make are **2 %** (71 % with one
hull per link, 14 % with the abduction-first yoke), and every real one is kept.

The abduction-first torso had one real contact at the end of the range: at
flexion −170° the upper arm's cheek pressed 1.4 mm into the yoke, and a policy
trained on it held its arms at −169.3° on 76–88 % of its steps, leaning on that
contact. Pitch-first there is nothing there to lean on.

### One pose v1 used that the real machine cannot hold

v1's reach optimisation reported its best pose as abduction +180°, flexion
−177°, elbow −114°, and derived 0.671 m from it. That pose puts the upper arm
through the torso — 102 000 mm³ of it. v1 would have collided there too; its
optimiser simply did not check. `_reach.py` enforces self-collision, and also
requires the COM to sit below the anchored hook (otherwise the "reach" is
measured from a hand the robot is standing on, which is how an early run of it
reported a nonsense 1.143 m). With both constraints the answer is 0.56 m on this
model (see "What the numbers are now" for why it is lower than both earlier figures).

## Sim2real: three numbers that are estimates, not datasheet

Everything else here is traceable. These three are not, and they are the first
things to identify on hardware.

**`armature` — reflected rotor inertia, N² · J_rotor.** v1 used `armature="0.01"`
for all 17 joints. A 64:1 AK80-64 reflects about **0.209 kg·m²** into its joint,
twenty times that, and more than any link's own inertia. A 36:1 AK45-36 reflects
0.0083. Getting this wrong makes a geared joint feel massless in simulation and
sluggish on the bench; it is the single largest sim2real term added here.
J_rotor itself is modelled as a disc holding 20 % of the actuator's mass at half
its outer radius, calibrated so an AK80-9 lands at the 2.4 × 10⁻³ kg·m² people
measure on that unit. **Identify it before trusting any transient.**

**`frictionloss`** is scaled from the one published backdrive figure (AK45-36,
0.8 N·m at 36:1) by gear ratio. Also to be identified.

**Actuator mass is booked entirely to the parent link.** The housing is bolted
to the parent and the rotor turns with the child; the rotor is a small fraction
of the whole, so the error is bounded by that fraction, and its inertia is in
`armature` where it belongs.

Two more honest caveats: the actuator's inertia tensor is a uniform cylinder of
its catalogue mass (the vendor STEP has no materials, so its volume cannot give
a mass), and the visual meshes are tessellated at 0.6 mm — exact geometry lives
in `cad/STEP/robot.step`.

## Verified

`python cad/tools/verify.py` — all 17 checks pass.

- Three vendor STEP files match their step.parts sha256, and their envelopes
  measured off the files match the datasheets: 61.9 × 98 × 98, 67 × 79 × 79,
  54 × 55 × 55 mm.
- All three canonicalised to +Z = joint axis, output flange at z = 0.
- Link masses sum to structure + actuators + payload (and lidars) = 24.1647 kg,
  and MuJoCo agrees to 1 mg.
- All 19 inertia tensors positive definite and obeying the triangle inequality.
- All 17 joints: axis, range and forcerange match spec and datasheet.
- Torque margin ≥ 1.37× peak over the entire joint box, ≥ 1.47× over the
  climbing envelope.
- No two actuator bodies intersect in any legal named pose (11 poses tested,
  including the keyframe, the arms flared 40° with the elbows bent, the −170°
  flexion stop, waist hard over while hanging, and elbows fully flexed).
- **Keyframe `hang_on_rung`** (`_gen_keyframe.py`): arms overhead at −160°, shoulder
  rotation 0, forearms rolled ∓5° — v1's posture. Both hooks on `rung_front_line_0`
  at y = ±0.155, throats facing the wall; the pendulum takes ~20 s to stop
  swinging, then the base drifts **under 0.01 mm per 5 s**. Hand forces 116 + 116 N
  against a 237.1 N robot, no joint above 4.3 N·m, no self-contact — the only
  other contact is the base resting on the wall, 14 N; the lidar cage stands clear.
- **Grip closed to `GRIP_SET` (−25°)**: holds 12 s untouched, `latched` and
  `grip_ok` true on both hands, no termination — v1's `climbing_env.py` runs
  against this scene unchanged.

Not checked: fastener stress, thermal duty cycle, wiring routing, stiffness
under load. The 3 mm wall thickness is set by handling and local buckling, not
stress — a 70 × 40 × 3 box section sees 15 MPa at 120 N·m and 6061-T6 yields at
276 — but no FEA was run.

## Regenerating

`meshes/` is in git (15 MB), so nothing below is needed to simulate or train.
`cad/STEP/` is not (regenerable), and neither is `cad/vendor/` — those files are
the manufacturers'. To rebuild the robot from a fresh clone:

```bash
python cad/tools/fetch_vendor.py   # 3 vendor STEP files, sha256 checked
python cad/src/robot.py            # the CAD assembly (STEP)
python cad/tools/gen_urdf.py       # URDF + meshes from the CAD
python urdf/_gen_scene.py         # scene.xml (drops the keyframe)
python urdf/_gen_keyframe.py --write   # find and verify the keyframe, write it back
python cad/tools/verify.py         # check everything
python -m rl.lessons && python -m rl.climb_task   # and what the RL task needs of it
```

Analysis, any time:

```bash
python cad/tools/check_fit.py --sweep 2000   # self-intersection, named poses + random
python cad/tools/torque.py 25000 urdf/scene.xml out.json [--envelope]
python urdf/_reach.py 60000                 # vertical reach, self-collision enforced
```
